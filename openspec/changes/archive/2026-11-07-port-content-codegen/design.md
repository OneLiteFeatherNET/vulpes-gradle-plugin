# Design

## Context

`vulpes-generator` (`origin/main`, `generation/java/*`) has five JavaPoet 1.13 generators that read vulpes-model entities from the database and write `<Type>Keys`, sealed `Custom<Type>s` and `<Type>Entries` into the `vulpes-base` clone. Render and write code is duplicated five times, and `sealed` is patched in by string replacement because JavaPoet 1.13 cannot express it. The expression function interface is generated by `ExpressionInterfaceGenerator` in the backend branch `themeinerlp/poc/evalex-expressions`. Inputs now come from the data JAR (`vulpes-format`), and `vulpes-base` offers the registration API of `invert-content-registration`.

## Decisions

### Module layout
`vulpes-format` (model, reader) ← `vulpes-codegen` (templates, generators, pure functions from `ContentRelease` + package to a list of `JavaFile`) ← `vulpes-gradle-plugin` (Gradle wiring). `vulpes-codegen` is unit-tested without Gradle, and generated sources are compiled in-process against `vulpes-base` in tests.

### JavaPoet
`com.palantir.javapoet` replaces `com.squareup:javapoet` 1.13: maintained, supports records and sealed types, so no string patching. One shared writer replaces the five copies of render/write.

### Generated shape (`minestom`, project `cygnus`, package `p`)
| Class | Content |
|-------|---------|
| `p.CygnusRelease` | as in `add-plugin-skeleton` |
| `p.CygnusItemKeys`, `…AttributeKeys`, `…SoundKeys`, `…FontSymbolKeys`, `…AdvancementKeys` | `Key` constants per entry, deprecated alias constants |
| `p.CygnusItems`, `…Attributes`, `…Sounds`, `…FontSymbols`, `…Advancements` | built entries (`CustomItem IRON_SWORD = CustomItem.of(…)`), deprecated alias constants pointing at the current constant, `List<…> ALL` |
| `p.CygnusContent` | `implements VulpesContent`, `INSTANCE`, returns the `ALL` lists and the alias map |
| `p.CygnusResourcePacks` | one `ResourcePackInfo` per pack (`id` = name-based UUID of the SHA-1, URI, hash) and `ALL` |
| `p.CygnusExpressionFunctions` | interface with one method per `interface` function; omitted when there is none |

Classes for a type without entries are still generated with an empty `ALL`. When the last entry of a type is removed, game code then fails only where it uses the removed constants, not because a whole class disappeared.

### Entry construction
- **Item**: `CustomItem.of(key, ItemComponents.apply(ItemStack.builder(Material.fromKey("<material>")).amount(<amount>), "<component>", "<json>", …).build())`. Components are passed as the raw JSON from the snapshot, sorted by component id.
- **Attribute**: `CustomAttribute.of(key, displayName, translationKey, minimum, default, maximum, synced)`.
- **Sound**: `CustomSound.of(key, null)` (no range in the contract).
- **Font symbol**: `CustomFontSymbol.of(key, Key.key("<font>"), new FontSymbol("<file>", "bitmap", ascent, height, List.of(<chars as unicode escapes>)))`.
- **Advancement**: `CustomAdvancement.builder(key).parent(<key or none>).icon(Material…).frame(FrameType.…).title(GsonComponentSerializer.gson().deserialize("<json>"))…build()`.
- **Expression interface**: port of `ExpressionInterfaceGenerator`: methods sorted by name (case-insensitive), `number` → `BigDecimal`, `boolean` → `boolean`, `string` → `String`, camel-case method names, description as Javadoc.

### Identifiers
Port of `JavaIdentifiers`: constant name from the key path (namespace dropped when it equals the project namespace, otherwise prefixed), upper snake case, leading digit prefixed with `_`, Java keywords avoided. `Claims` per class detects two keys with the same constant name and fails with both keys. Alias constants take part in the same claim set.

### Templates
```java
public interface Template {
    String name();
    Set<EntityType> supportedTypes();
    List<Dependency> runtimeDependencies(); // coordinates the plugin adds to implementation
    List<JavaFile> generate(ContentRelease content, String packageName);
}
```
Templates are registered in the plugin (no extension point yet). `vulpesGenerate` gets the template name as `@Input`; unknown names fail and list the known ones. The plugin adds the runtime dependencies of the selected template to `implementation` lazily (`withDependencies`), with versions fixed at plugin build time (generated resource), so Renovate updates them together with the plugin.

### Determinism
Entries are generated in contract order (sorted by key); output files are written with `\n` line endings and no timestamps, so equal input produces equal bytes and the build cache stays effective.

## Testing (F.I.R.S.T.)

- Unit tests per generator on small in-memory snapshots: identifiers and collisions, aliases, every field of every type, empty types, expression type mapping.
- Compile tests: generated sources of the fixture snapshot compile in-process against `vulpes-base` (template `minestom`) and against `adventure-key` (template `keys`).
- Golden test: the generated sources of the fixture snapshot equal checked-in expected files; updating them is an explicit step.
- TestKit: template selection, unknown template, unsupported entity type, dependency added for each template.

## Risks

- **vulpes-base API churn**: the template is tied to one `vulpes-base` major; the plugin pins the version it was tested with.
- **Fixture coverage**: the backend does not deliver format 1 yet; generators are tested against the contract fixtures only until then.
