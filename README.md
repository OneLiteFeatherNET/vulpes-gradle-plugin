# Vulpes Gradle Plugin

Generates Java code from Vulpes content releases (`net.onelitefeather.vulpes.content:<project>:<version>`) during the game's build.

## Usage

Apply the plugin with the `java` or `java-library` plugin. Both `pluginManagement` and the dependency resolution need the OneLiteFeather repository, which requires credentials (`ONELITEFEATHER_MAVEN_USERNAME` and `ONELITEFEATHER_MAVEN_PASSWORD`).

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        gradlePluginPortal()
        maven {
            url = uri("https://repo.onelitefeather.dev/onelitefeather")
            credentials {
                username = System.getenv("ONELITEFEATHER_MAVEN_USERNAME")
                password = System.getenv("ONELITEFEATHER_MAVEN_PASSWORD")
            }
        }
    }
}

dependencyResolutionManagement {
    repositories {
        mavenCentral()
        maven {
            url = uri("https://repo.onelitefeather.dev/onelitefeather")
            credentials {
                username = System.getenv("ONELITEFEATHER_MAVEN_USERNAME")
                password = System.getenv("ONELITEFEATHER_MAVEN_PASSWORD")
            }
        }
    }
}
```

```kotlin
// build.gradle.kts
plugins {
    java
    id("net.onelitefeather.vulpes") version "0.2.0"
}

dependencies {
    vulpes("net.onelitefeather.vulpes.content:cygnus:1.4.0")
}

vulpes {
    // "minestom" (default) or "keys"
    template = "minestom"
    // Java package of the generated code; the default is net.onelitefeather.vulpes.content.<project>
    packageName = "com.example.game.content"
}
```

Each content project in the `vulpes` configuration generates sources into `build/generated/sources/vulpes/java/main` before `compileJava` runs.

- `minestom` (default) generates the full content: entries, the content object, resource packs and formulas. It needs vulpes-base, which the plugin adds as a runtime dependency. vulpes-base does not bring Minestom or the Adventure API, so the game must have both on its compile classpath itself, as every Minestom game already does.
- `keys` generates the key constants and the expression function interface only. It needs adventure-key and no server.

With several content projects, set the package per project with `vulpes { project("cygnus") { packageName = "..." } }`. `vulpes.packageName` is only allowed for a single content project.

### Start the server

Bootstrap the generated content once, after `MinecraftServer.init()`:

```java
MinecraftServer.init();
VulpesRegistries registries = Vulpes.bootstrap(CygnusContent.INSTANCE);
```

### Expression functions

Content can call functions that the game implements. Implement the generated `CygnusExpressionFunctions` interface, then create `CygnusFormulas` once at start-up and call its typed methods:

```java
CygnusFormulas formulas = new CygnusFormulas(new GameExpressionFunctions());

BigDecimal damage = formulas.armorDamage(new BigDecimal("100"), new BigDecimal("25"));
if (damage.compareTo(new BigDecimal("75")) == 0) {
    // ...
}
String shown = damage.toPlainString();
```

Numbers are `BigDecimal`. Compare them with `compareTo`, not `equals`, and print them with `toPlainString`: the expression engine strips trailing zeros, so `toString` can print `30` as `3E+1`.

`CygnusFormulas` is generated by the `minestom` template only.

### Snapshot versions

Gradle caches changing modules, such as `-SNAPSHOT` content, for 24 hours. To pick up a new snapshot right away, either run with `--refresh-dependencies` or disable the cache for the plugin's resolvable configuration:

```kotlin
configurations.named("vulpesData") {
    resolutionStrategy.cacheChangingModulesFor(0, "seconds")
}
```

### Compare releases

```sh
./gradlew vulpesDiff -Pvulpes.diff.from=1.3.0
./gradlew vulpesDiff -Pvulpes.diff.from=1.3.0 -Pvulpes.diff.project=cygnus
```

The task compares the current content with the given version and writes a Markdown and a JSON report per content project to `build/reports/vulpes/diff/`. `vulpes.diff.project` limits the comparison to one content project.

## Using the code generator as a library

The generator is published as two Maven artifacts with the plugin's version, released together with it:

```kotlin
dependencies {
    implementation("net.onelitefeather.vulpes:vulpes-codegen:<version>")
}
```

`vulpes-codegen` brings `vulpes-format` (the reader of content releases) as a compile dependency. JavaPoet and EvalEx are runtime dependencies. Test libraries are not published.

The entry point is `net.onelitefeather.vulpes.codegen.VulpesCodegen`. It takes a content release, read by `vulpes-format` with `ContentReader.read(source, releaseJson, snapshotJson)`, and the options: the package of the generated classes and a template, `minestom` or `keys`.

```java
ContentRelease content = ContentReader.read("cygnus", releaseJson, snapshotJson);
CodegenOptions options = new CodegenOptions("net.example.content.cygnus", CodegenTemplate.MINESTOM);

List<GeneratedSource> sources = VulpesCodegen.generate(content, options);
VulpesCodegen.write(content, options, outputDirectory);
```

`generate` returns the sources in memory. `write` creates the files in package layout below the directory and nothing else; clear the directory first if old files must go. Generation fails with `CodegenException`, which names the project, for example for a font in the reserved namespace `space`.

The output is the same as the plugin's output for the same release, package and template.

### Compatibility

Semantic versioning covers `VulpesCodegen`, `CodegenOptions`, the names of `CodegenTemplate`, `GeneratedSource`, `Dependency`, `CodegenException` and the `vulpes-format` types in their signatures. Everything else in `vulpes-codegen` is internal (`net.onelitefeather.vulpes.codegen.internal`) and may change in any release. A breaking change of a covered type is marked with `!` and a `BREAKING CHANGE:` footer.

Generated code is not covered by semantic versioning. A release that changes the code generated for a template names that template in the changelog.

## Testing content locally

A local build of content, such as the ZIP that Stelaris offers as a "local build" download before a release is published, can be tested without publishing it. Unzip it into the game's project root, so that the project holds these files:

```
game/
└── vulpes/
    └── cygnus/
        ├── release.json
        └── snapshot.json
```

The local entries are merged over the published data JAR of the same declared project, so a build with a few changed or new entries does not need a copy of the whole published content:

- Entries are matched by their stable `id`; assets are matched by `path`. A local entry whose id exists in the published content replaces that entry as a whole. A local entry with a new id is added. Published entries without a local counterpart are kept.
- A rename keeps the id: the local entry with the new key replaces the published one, and the old key is gone from the build.
- Entries cannot be deleted. An entry that the local snapshot does not contain stays in the build.
- `projectId` and `namespace` must equal the published ones. The pack and the release (version, revision and base) come from the local files.
- The rules that relate entries to each other (unique ids and keys, previous keys, asset paths, expression names, advancement parents) are checked on the merged content. A failure names both entries and whether each one comes from the local or the published side.

For a merged project the Maven artifact is still resolved, because the merge needs the published content, so the repository credentials are still needed. Remove the directory to build from the published content alone. Add `/vulpes/` to `.gitignore`, so that local files are not committed.

A content project that has no published release yet can be tested the same way. Declare its `vulpes(...)` line with the version it will be published under, for example `0.1.0-SNAPSHOT`, and keep the local directory. When no data JAR of that coordinate resolves, the local files are used alone, and the build does not need the Maven artifact. Once the release is published and resolves, the build merges the local files over it, and the notice names the published version.

Every build prints one line per merged project, with the local version, the published version it is merged over, the number of replaced and added entries, and the base branch and commit recorded in `release.json`:

```
vulpes local content: cygnus 1.4.1-SNAPSHOT is merged over published 1.4.0 from vulpes/cygnus: 3 replaced, 2 added; base ... branch main commit ...
```

For a project without a published release, the build prints one line that names the local version, the declared coordinate and the reason the data JAR did not resolve:

```
vulpes local content: cygnus 0.1.0-SNAPSHOT: no published release used, local content only; could not resolve net.onelitefeather.vulpes.content:cygnus:0.1.0-SNAPSHOT: not found; base ...
```

- A directory with only one of the two files fails the build and names the missing file.
- A declared project whose data JAR does not resolve and that has no local directory fails the build, and the message names the coordinate and the reason.
- A directory for a project that no `vulpes(...)` dependency declares is ignored with a warning. It adds no content.
- `vulpes { localContentDirectory = "content" }` changes the parent directory, which is relative to the project directory and defaults to `vulpes`.
- In CI, run with `-Pvulpes.local.forbid=true`. The build then fails when a declared project is merged with a local directory, and when a local directory is used alone, which names the coordinate and the reason. A missing publish therefore never passes CI silently.
- A `release.json` in format 2 may carry a `base` record with `repository`, `branch` and `commit`. Older plugin versions reject format 2, so the generator writes it only once a plugin release that reads it is available.
